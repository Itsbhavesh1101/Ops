## 1. Executive Summary

The E-7 Operations Engine requires enterprise Single Sign-On (SSO) for all interactive human browser sessions. The demonstration environment utilized an isolated Keycloak provider with PKCE, while the accepted Stage 4 production Google Workspace implementation uses an OpenID Connect ID-token flow with client-side CSRF state and cryptographic nonce verification, URL fragment scrubbing, and server-side cryptographic RS256 verification via Google's public JWKS.

During Phase 8 development and demonstration, E-7 utilized an isolated, air-gapped Keycloak 24.0.5 container strictly to validate cryptographic token verification (RS256, JWKS caching, clock skew bounds, claims resolution). For production V1, E-7 requires integration with the corporate Google Workspace / Google Cloud Identity OpenID Connect infrastructure.

No demonstration or mock identity provider is permitted in production environments.

## 2. Distinction Between Existing Implementation and Company Provisioning

To ensure clear operational boundaries between E-7 engineering and Corporate IT, responsibilities are partitioned as follows:

| Component / Layer | Existing Internal Implementation (Complete) | Company-Owned External Provisioning (Required) |
|---|---|---|
| **Cryptographic Verifier** | `GoogleOidcVerifier` verifies RS256 signatures against Google JWKS, validates `iss`, `aud`, `exp`, `nbf`, clock skew (<=60s), and `hd`. Subject-first identity binding and recycled-email protection are strictly enforced. | Google Cloud Console project registration and public OAuth 2.0 Web Client provisioning. |
| **Frontend Authentication** | React SPA executes OpenID Connect ID-Token flow (`response_type=id_token`) with ephemeral state and nonce stored in `sessionStorage`; scrubs URL fragment immediately upon receipt; tokens held strictly in memory. | Authorized JavaScript origins and Redirect URIs registered on Google OAuth Client. |
| **Directory & Lifecycle** | Fail-closed identity rejection for unmapped principals (`auth.principal_unresolved`). | Corporate Google Workspace directory: user onboarding, suspension, termination, and hardware MFA/2FA. |
| **Authorization & Scoping** | Internal E-7 RBAC engine assigns tenant membership and roles (`planner`, `approver`, `tenant_admin`, etc.). | Institutional directory group rosters and corporate email provisioning. |
| **Machine-to-Machine** | Separate service API key infrastructure (`X-E7-Service-Key`, `e7sk_...`) strictly isolated from human OIDC. | External service provisioning if integrated into external orchestration. |

## 3. OAuth 2.0 Web Client Registration Requirements

The Corporate IAM Team is requested to register an OAuth 2.0 Client in the enterprise Google Cloud Console:

| Parameter | Specification | Purpose / Rationale |
|---|---|---|
| **Application Type** | **Web Application (Public Client)** | Single Page Application (React SPA) communicating with FastAPI Backend. |
| **Application Name** | `E-7 Operations Engine` | Displayed on Google OAuth consent screen. |
| **Client ID** | Generated by Google Console (e.g. `<client-id>.apps.googleusercontent.com`) | Audience identifier verified by both frontend and backend token verifier. |
| **Client Secret** | **NONE REQUIRED (Public Client)** | **Per RFC 7636 and OIDC Core 1.0, public browser SPAs must NEVER hold client secrets.** No client secret should be generated or distributed for browser clients. |
| **Authorized JavaScript Origins** | `https://<production-domain>`<br/>`https://<staging-domain>` | Required for browser-based OAuth/OIDC redirection. |
| **Authorized Redirect URIs** | `https://<production-domain>/login` | Endpoints handling OAuth/OIDC ID-token returns. |
| **Allowed Hosted Domains (`hd`)** | Institutional corporate domain (e.g. `irinfotech.com`) | Enforced strictly by backend token verifier to reject external accounts. |
| **OIDC Scopes** | `openid`, `email`, `profile` | Minimum required OIDC claims. |

> [!IMPORTANT]
> **No Client Secret for Public SPAs:** Because the E-7 frontend is a public client executing the accepted custom ID-token flow, no client secret is required or permitted. If Corporate IT policies require a confidential backend proxy client, that client must be separately registered and its secret managed strictly in backend secret storage.

## 4. Cryptographic Token Verification Architecture

The E-7 backend enforces asymmetric token verification via [GoogleOidcVerifier](file:///f:/operations-engine/app/core/auth/google_oidc.py):
1. **Issuer Verification:** `iss` must strictly equal `https://accounts.google.com` or `accounts.google.com`.
2. **Discovery Endpoint:** Pinned to canonical `https://accounts.google.com/.well-known/openid-configuration`.
3. **JWKS Key Verification:** Public keys fetched over TLS from `https://www.googleapis.com/oauth2/v3/certs`. Verified using RS256. Symmetric algorithms (`HS256`, `HS384`) or `none` algorithm are rejected at header inspection.
4. **Key Caching & Fallback:** JWKS public certificates are cached with dynamic `Cache-Control` TTL (bounded between 1 hour fallback and 24 hours max). Single-flight locked cache refresh on unknown `kid`.
5. **Clock Skew Tolerance:** Maximum 60-second leeway enforced on `exp` and `iat` claims.
6. **Audience Enforcement:** `aud` claim must match one of the configured production Client IDs. Multi-audience tokens require `azp` validation.
7. **Verified Email Enforcement:** `email_verified` claim must equal `true`. Unverified email claims fail closed.
8. **Hosted Domain Enforcement:** `hd` claim must match configured corporate domain allowlist.

## 5. Identity-to-Principal & Tenant Mapping Governance

### 5.1 The Authorization Boundary Principle
A valid Google Workspace identity proves cryptographic identity only. It carries **zero intrinsic tenant authorization or administrative privileges** within E-7.

* **No Automatic Admin Assignment:** External identity claims (including email usernames containing `admin` or Google group memberships) must never automatically grant E-7 `tenant_admin` privileges.
* **Fail-Closed Unmapped Identities:** Authenticated Google users who lack an explicit entry in the internal E-7 identity mapping table are rejected with `HTTP 401 Unauthorized: Verified OIDC identity is not mapped to an active E-7 principal.`

### 5.2 Directory Ownership & Lifecycle
* **Corporate IT / IAM Team:** Owns user lifecycle in Google Workspace (creation, departmental allocation, MFA enforcement, account suspension, and termination). When an employee departs, disabling their Google Workspace account immediately invalidates their ability to acquire new OIDC tokens.
* **E-7 Tenant Administration:** Owns internal tenant assignment and RBAC role assignment in E-7 persistent storage (`user_roles`). User onboarding to E-7 requires mapping the corporate email address (`email`) to an authoritative internal tenant UUID.

### 5.3 Canonical RBAC Roles
E-7 enforces canonical Role-Based Access Control (RBAC) across 7 discrete roles:
* `planner`: Author of operational goals and schedule requests.
* `approver`: Reviews and signs off on generated plans and schedule publications.
* `scheduler`: Submits and manages solver jobs.
* `operator`: Executes runtime human tasks and workflow actions.
* `tenant_admin`: Manages tenant configuration, service API keys, and workflow models.
* `auditor`: Read-only access to immutable audit ledgers.
* `viewer`: Read-only visibility across operational dashboards.

## 7. Production Verification Procedure

Prior to production sign-off, Corporate IT and E-7 Engineering execute the following technical checks:

### Step 1: Network & Discovery Verification
Verify outbound HTTPS connectivity to Google accounts from the production network:
```bash
curl -fsS https://accounts.google.com/.well-known/openid-configuration | grep "jwks_uri"
```

### Step 2: JWKS Public Key Retrieval
```bash
curl -fsS https://www.googleapis.com/oauth2/v3/certs | grep "keys"
```

### Step 3: Backend Token Verifier Self-Check
```bash
python -c "
from app.core.auth.google_oidc import GoogleOidcVerifier
verifier = GoogleOidcVerifier(
    client_ids=['<client-id>.apps.googleusercontent.com'],
    allowed_hosted_domains=['<corporate-domain>']
)
print('OIDC_VERIFIER_INIT_PASS: Google OIDC verifier successfully initialized.')
"
```

### Step 4: Interactive ID-Token Login Verification
1. Navigate to `https://<production-domain>/login`.
2. Click Single Sign-On; verify redirection to `https://accounts.google.com/o/oauth2/v2/auth` with `response_type=id_token`, `state`, and `nonce`.
3. Complete authentication with corporate Google account.
4. Verify redirection to `https://<production-domain>/login#id_token=...&state=...`.
5. Verify browser validates `state` and token `nonce`, scrubs the URL fragment immediately via `history.replaceState`, and passes token to `/api/v1/auth/me`.
6. Verify token is stored **strictly in memory** (inspect `localStorage` and `sessionStorage` to confirm zero token persistence).

### Step 5: Negative Security Tests
1. **Wrong Domain Test:** Attempt login with a personal `@gmail.com` account. Verify backend verifier rejects with `HostedDomainRejectedError` (`HTTP 401 Unauthorized`).
2. **Unmapped Identity Test:** Authenticate with a valid corporate account that has not been mapped in E-7. Verify backend returns `HTTP 401 Unauthorized: Verified OIDC identity is not mapped to an active E-7 principal.`
3. **Demo Provider Isolation Test:** Verify backend in production mode refuses to start if configured with `E7_OIDC_PROVIDER_NAME=keycloak`.

## 9. Unresolved Production Considerations & Architectural Limitations

Prior to live enterprise deployment, Corporate IT and Security Architecture must explicitly review the following operational constraints:

1. **Custom ID-Token Implicit Flow in SPA:** The current browser login implementation utilizes an OpenID Connect ID-token implicit callback (`/login#id_token=...`) to avoid browser CORS restrictions against `https://oauth2.googleapis.com/token` without exposing client secrets.
2. **Google Identity Services (GIS) Recommendation:** Google officially recommends Google Identity Services (GIS) SDK (`https://accounts.google.com/gsi/client`) for web authentication. Migrating from the redirect-based flow to GIS credential callbacks represents a future frontend enhancement.
3. **Bearer Token Replay Scope:** While browser callback replay is prevented through atomic single-use session retrieval (`retrieveAndClearOidcSession()`), signed bearer ID tokens remain valid until their `exp` timestamp. Token interception at the network layer is mitigated exclusively by TLS termination.
4. **Unverified Live Interoperability:** End-to-end authentication against production Google Workspace accounts remains unverified until corporate Google Cloud Console credentials and domain DNS records are provisioned.
5. **Configuration-Backed Human User Provisioning:** Interactive human users are mapped via server-controlled JSON configuration (`E7_OIDC_USER_MAPPINGS_JSON`) rather than an internal persistent PostgreSQL user management table. Dynamic user creation or modification requires updating configuration and restarting/reloading the application.
6. **Revocation Semantics & Operational Procedures:** Revoking user access currently requires disabling the user in Google Workspace (preventing new token issuance) and removing the user entry from `E7_OIDC_USER_MAPPINGS_JSON`. Immediate mid-session invalidation of issued tokens requires implementing a distributed token-denylist cache.
